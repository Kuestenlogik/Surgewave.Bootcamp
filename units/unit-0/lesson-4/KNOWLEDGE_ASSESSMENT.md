# Knowledge Assessment: Lesson 0.4 - Contributing to Surgewave

Test your understanding of how to contribute to the Surgewave project.

## Multiple Choice

### 1. Where should you report a bug in Surgewave?

- [ ] A) Email the developers directly
- [ ] B) Post on Reddit
- [ ] C) Create a GitHub Issue with reproduction steps
- [ ] D) Tweet about it

<details>
<summary>Answer</summary>

**C)** Create a GitHub Issue with reproduction steps.

GitHub Issues is the official channel for bug reports. Include version info, steps to reproduce, expected vs actual behavior, and relevant logs.
</details>

### 2. What should you do before submitting a bug report?

- [ ] A) Search existing issues to see if it's already reported
- [ ] B) Try the latest version to see if it's fixed
- [ ] C) Check the documentation for solutions
- [ ] D) All of the above

<details>
<summary>Answer</summary>

**D)** All of the above.

Before reporting, search existing issues, try the latest version, and check documentation. This saves time for both you and maintainers.
</details>

### 3. What is the correct commit message format for Surgewave?

- [ ] A) Any format is fine
- [ ] B) `<type>(<scope>): <description>`
- [ ] C) Just the description
- [ ] D) `[TICKET-123] description`

<details>
<summary>Answer</summary>

**B)** `<type>(<scope>): <description>`

Surgewave uses conventional commits format with types like `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `chore`.
</details>

## True/False

### 4. You need permission before forking the Surgewave repository.

- [ ] True
- [ ] False

<details>
<summary>Answer</summary>

**False** - Surgewave is open source. Anyone can fork the repository and submit pull requests.
</details>

### 5. Documentation improvements are considered valuable contributions.

- [ ] True
- [ ] False

<details>
<summary>Answer</summary>

**True** - Documentation improvements (typo fixes, clarifications, examples) are always welcome and help the entire community.
</details>

## Short Answer

### 6. List three things a good bug report should include.

<details>
<summary>Answer</summary>

A good bug report should include:
1. Steps to reproduce the issue
2. Expected behavior vs actual behavior
3. Environment information (Surgewave version, .NET version, OS)
4. Error messages or logs
5. Minimal code sample if applicable
</details>

### 7. What is the workflow for submitting a code contribution?

<details>
<summary>Answer</summary>

1. Fork the repository
2. Clone your fork locally
3. Create a feature branch
4. Make changes and add tests
5. Commit with proper message format
6. Push to your fork
7. Create a Pull Request
8. Address review feedback
9. Wait for approval and merge
</details>
